class VirtualC64

Defined in VirtualC64.h:2053

Public API

This class declares the emulator's public API. It consists of functions controlling the execution state, such as running or pausing the emulator, as well as functions configuring the various components. The class contains separate sub-APIs for the subcomponents of the emulator. For example, a VICII API provides additional functions that interact directly with the VICII graphics chip.

void powerOn()

Defined in VirtualC64.h:2238

Switches the emulator on.

Powering on the emulator changes the internal state to ExecState::PAUSED, the same state that is entered when the user hits the pause button. Calling this function on an already powered-on emulator has no effect.

The function returns when the emulator thread has carried out the request. A failure throws the corresponding exception.

Exceptions ​

ExceptionDescription
CoreError(CoreError::NOT_LAUNCHED) if the emulator thread cannot carry out the request, because it has not been launched yet, is halted or suspended. The same applies if the function is called from the emulator thread. Use powerOnAsync() in these situations.

void run()

Defined in VirtualC64.h:2286

Starts emulation.

Running the emulator changes the internal state to ExecState::RUNNING, which is the normal operation state. Frames are computed at normal pace, if warp mode is switched off, or as fast as possible, if warp mode is switched on. If this function is called for a powered-off emulator, an implicit call to powerOn() will be performed.

The function returns when the emulator has been started.

Exceptions ​

ExceptionDescription
CoreErrorif the emulator is not ready to run (see checkReady()).
CoreError(CoreError::NOT_LAUNCHED) if the emulator thread cannot carry out the request, because it has not been launched yet, is halted or suspended. The same applies if the function is called from the emulator thread. Use runAsync() in these situations.

halt ​

cpp
void halt()

Defined in VirtualC64.h:2380

Terminates the emulator thread.

Halting the emulator changes the internal state to ExecState::HALTED. This state is part of the shutdown procedure and never entered during normal operation.

NOTE

The function blocks until the emulator thread has terminated. It does nothing if there is no running emulator thread (e.g., if the thread has already been halted), so it is safe to call it more than once. It throws a CoreError if the calling thread has suspended the emulator thread, because a suspended thread cannot terminate.

stepOver ​

cpp
void stepOver()

Defined in VirtualC64.h:2539

Steps over the current instruction.

Runs the emulator until the instruction following the current instruction has been reached. The emulator must not be running. The CPU debugger utilizes this function to implement single stepping.

stepOver() acts like stepInto() except for branching instructions. For instance, if the current instruction is a JSR instruction, the subroutine will be executed in a single chunk.

NOTE

If the current instruction is a branch instruction which never returns, the emulator will remain in running state. Calling this function will then be equivalent to a calling run(), with the exception of a small runtime overhead since the emulator will check after the each instruction if the program counter has reached its target location.

The function returns when the emulator has been started for the step. It is paused again when the step is done.

Exceptions ​

ExceptionDescription
CoreError(CoreError::RUNNING) if the emulator is already running.
CoreErrorif the emulator is not ready to run (see checkReady()).
CoreError(CoreError::NOT_LAUNCHED) if the emulator thread cannot carry out the request (see put()).

wakeUp ​

void wakeUp()

Defined in VirtualC64.h:2596

Sends a wakeup signal to the emulator thread.

To compute frames at the proper pace, the emulator core expects the GUI to send a wakeup signal on each VSYNC pulse. Once this signal is received, the emulator thread starts computing all missing frames. To minimize jitter, the wakeup signal should be sent right after the current texture has been handed over to the GPU.

callAsync ​

void callAsync(std::function< void()> fn, std::function< void(std::exception_ptr)> done = nullptr)

Defined in VirtualC64.h:2851

Queues a function for the emulator thread without waiting for it.

WARNING

This is an advanced interface. It bypasses the dedicated API functions, and what it touches is not covered by any compatibility promise.

This is the asynchronous counterpart of call(). The function is carried out by the emulator thread at some later time, so everything it refers to must stay valid until then. A failure of the function cannot be passed on to the caller. If 'done' is given, it is called on the emulator thread when the function has been carried out, with the exception it threw (or null). It is also called, on the calling thread, if the command queue is full and the request is dropped. Nothing is carried out as long as the emulator thread has not been launched.

put ​

void put(const Command & cmd, const std::string & str = "")

Defined in VirtualC64.h:2874

Feeds a command into the command queue and waits for the result.

WARNING

This is an advanced interface. It bypasses the dedicated API functions, and what it touches is not covered by any compatibility promise.

The function returns when the emulator thread has carried out the command. A command that fails throws the corresponding exception.

Because the queue is processed in order, all commands issued earlier (e.g., via putAsync()) have been carried out when the call returns. Commands that carry a pointer to an object of the caller can rely on that object being alive for the whole duration of the command.

Exceptions ​

ExceptionDescription
CoreError(CoreError::NOT_LAUNCHED) if the emulator thread cannot carry out the command, because it has not been launched yet, is halted or suspended. The same applies if the function is called from the emulator thread. Use putAsync() in these situations (it can also be called before the emulator thread is launched, in which case the command is carried out at launch), and for events that occur at a high rate (e.g., key presses or mouse movements).
